# clarify (`pbakaus/impeccable/clarify`)

## whitebox

- 前置准备: 调用 /impeccable 载入设计原则与上下文收集协议; 若尚无设计上下文, 必须先运行 /impeccable teach, 并额外收集受众技术水平与用户当下的心理状态
- 诊断原文案: 按 7 类问题清单逐项排查——术语、歧义、被动语态、长度、预设用户知识、缺失上下文、语气错配, 同时确认受众/用户心理状态/期望动作/空间等约束
- 规划改写策略: 确定唯一核心信息、用户下一步动作、应有语气、硬约束 (字数上限、品牌声音、本地化)
- 分类改写: 按文案类型逐区处理——报错、表单标签、按钮/CTA、帮助与提示、空状态、成功提示、加载状态、确认弹窗、导航标签, 每区套用对应改写原则
- 验证效果: 用五项标准复核——无上下文也能看懂、知道下一步做什么、足够简洁、术语与全局一致、语气匹配场景

- 对照模板改写 (核心转换): 内置 bad→good 对照库覆盖 9 类界面文案, 例如 'Error 403: Forbidden' → '你没有权限查看此页, 请联系管理员开通'; 'Are you sure?' → '删除项目 Alpha? 此操作不可撤销', 逐类把问题文案映射为原则化新文案
- 双重过滤校验: 改写结果须同时通过 6 条清晰原则 (具体、简洁、主动语态、人性化、有帮助、术语一致) 和禁止清单 (不得指责用户、不得用术语不解释、不得含糊到无解释、占位符不得当唯一标签等)
- 外部依赖仅一个 skill: /impeccable (提供设计原则、反模式与上下文收集协议, 属强制前置步骤); 无任何库、工具或模型 API 依赖, 全部为提示词层面的规则驱动执行
