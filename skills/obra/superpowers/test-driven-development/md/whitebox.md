# test-driven-development (`obra/superpowers/test-driven-development`)

## whitebox

- RED: 针对目标行为先写一个最小化的失败测试（一个测试只测一个行为）
- 验证 RED: 实际运行测试，确认它「失败」而非「报错」，且失败原因正是功能缺失
- GREEN: 写刚好能让该测试通过的最少代码，不多做任何事
- 验证 GREEN: 运行全部测试，确认新测试通过、旧测试不挂、输出干净
- REFACTOR: 在保持绿色（测试通过）的前提下去重复、改命名，然后进入下一个 RED

- 核心闸门是「先见失败再写实现」（Iron Law：没有失败过的测试不允许写产品代码），验证手段是实际调用项目的测试运行器（如 `npm test`，示例使用 jest + TypeScript），而非人工目测；无外部模型 API 依赖
- 每次阶段切换以「亲眼观察到失败/通过」为条件：测试若直接通过说明在测已有行为而非新需求；失败原因不对（如拼错）则修测试不修代码——保证测试本身被证明有捕获缺陷的能力
- 内置反合理化机制：列出常见借口（太简单不用测、事后补测、留着当参考等）并逐条驳斥，触发红旗即「删除代码、回到 RED 重来」；修 bug 也走同一循环——先写能复现 bug 的失败测试
