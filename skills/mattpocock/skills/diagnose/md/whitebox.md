# diagnose (`mattpocock/skills/diagnose`)

## whitebox

- 搭反馈回路：为 bug 构造一个快速、确定、可自动运行的 pass/fail 信号（失败测试 / curl / 脚本均可），这是后面一切判断的唯一信号源
- 跑回路复现：确认复现的是用户描述的那个故障（而非附近另一个 bug），且能稳定复现
- 列假设：先写 3~5 条可证伪假设并排序，给用户过目以便快速纠偏（不阻塞，用户不在线就按自己的排序继续）
- 逐变量验证：一次只改一个变量，靠调试器或带 [DEBUG-xxxx] 前缀的定向日志区分假设；性能回归则先测基线再二分，不靠日志
- 修 + 回归 + 收尾：回归测试先行（写→看它失败→修→看它通过），清理全部调试代码，把命中假设写进 commit 信息

- 反馈回路构造器：按优先级尝试约 10 种手段——失败测试 → curl/CLI 与快照 diff → 无头浏览器 (Playwright/Puppeteer) → 重放抓包 (HAR/trace) → 一次性最小 harness → fuzz 循环 → git bisect run 自动二分 → 新旧版本差分 → 人工 bash 脚本兜底；偶发 bug 则加压/并行/缩窗口，把复现率拉到可调试水平。回路本身也会被持续迭代：更快、信号更锐、更确定
- 可证伪假设纪律：每条假设必须附预测（'若 X 是因，改 Y 则 bug 消失'），说不出预测的视为感觉、直接丢弃；先列 3~5 条排序，防止锚定在第一个想到的方案上
- 无回路就停：实在建不出自动回路时明确告知，向用户索要 (a) 能复现的环境 (b) 抓包产物（HAR / 日志 / core dump）(c) 生产埋点许可——绝不凭空猜测进入假设阶段；若最终发现回归测试找不到正确接缝，这本身就是结论，会记录并交接架构改进建议
